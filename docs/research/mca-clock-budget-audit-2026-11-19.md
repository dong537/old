# MCA 校时预算空耗审计（2026-11-19）

## 观察与根因

`tree-20261119-auto-001` 至 `-005` 各登记 20 个站点请求预算槽，但每批只新增 13 份地区树响应；五批均无 429 和收集错误。以 `-005` 为例，小时账本在北京时间 07:24:26–07:45:18 有 20 个时间戳，原始 GET 响应文件对应 13 个时间戳。其余时间戳未保存原始 HTTP 内容，因此无法单靠缓存精确证明每次实际发送的请求方法。

代码路径可以解释其中的额外开销：`ServerClock` 的有效期为 300 秒，串行请求间隔为至少 60 秒。`fetch_child()` 先校时，再调用 `limiter.wait()` 记录一个预算槽，最后在发送 GET 前检查校时是否已过期。如果校时恰好在等待期间过期，这个预算槽已记入小时账本，却不会发出 GET；随后需再用一个预算槽发送校时 HEAD，并再等待一个 GET 槽。07:29:55/07:31:05、07:36:33/07:37:37 和 07:43:13/07:44:14 的连续未保存时间戳与该路径吻合。

## 修正

在 `ServerClock.timestamp_ms(limiter)` 中提前检查当前校时的剩余有效期能否覆盖下一次请求的最大节流等待（`interval + jitter`）及 5 秒余量。如果不能，则先使用同一站点预算重校时，再预约下一次 GET/POST。发送前的第二次校时检查、失败停机、全站锁、每小时最多 60 次账本和 429 冷却均保留。这个修正不提高对官网的请求速率上限，也不改变历史缓存。

## 成功响应 Date 复用（后续离线评估）

地区树现有 106 份响应文件中，104 份是独立 HTTP GET 原件（其余两份为旧 JSON 种子）；104/104 均带可解析的 `Date`。官网时间相对本机请求中点的偏差按 HTTP 秒精度中点计算为 6.19–7.28 秒，中位数 6.74 秒；请求读取耗时为 0.164–0.977 秒。成功 GET 的签名时间与该时间源一致。POST 代码原本也读取 `Date`，但历史成功 wrapper 未保存该头，故本轮不能离线量化历史 POST 的 Date 覆盖率。

现允许**成功、HTTP 200、业务码 0** 的 GET/POST 响应续新校时 TTL：只接受有时区、响应读取不超过 5 秒、偏差不超过 60 秒且与上一次 HEAD 校准偏差不超过 3 秒的 Date；缺失、格式错误、异常偏差或慢响应都忽略，届时仍按原有 HEAD 途径重新校时。HEAD 原始偏差是固定锚，成功响应不能把时钟逐次推离该锚；业务错误、429 和 5xx 不参与续新。新保存的 POST 原始 wrapper 增加 `responseDate` 与 `signedTimestampMs` 便于后续复核，旧文件不改。

离线 TDD 已覆盖有效 Date 续新、缺失/异常 Date 不续新，以及真实 GET/POST 适配器调用；测试先见预期失败，再修复。若后续响应持续提供一致 Date，一个 20 请求批次预计为一次 HEAD 加至多 19 次 GET/POST，较此前树批次的 13 份新响应有潜在收益；这是**代码预算估计**，须在新启动批次实测，不能把它当作已获取记录数。全站锁、单线程间隔、小时 60 次上限和 429 冷却未放宽。
